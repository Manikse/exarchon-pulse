# EXARCHON-PULSE — Довідник команд консолі

Це довідник по `PulseConsole` — інтерактивній консолі, яка запускається разом з
демоном командою `python main.py` (промпт `Pulse>`). Демон і консоль працюють
паралельно: демон у фоновому потоці кожні 10с опитує GitHub і локальні нотатки,
консоль — інтерфейс керування та звітності в головному потоці.

Вбудована команда `help` (або `?`) виводить список усіх команд, але змістовний
опис (`help <команда>`) є лише там, де в коді є docstring — нижче описано геть
усе, включно з тим, що docstring не має.

## Швидкий довідник

| Команда | Що робить |
|---|---|
| `report [day\|week\|month\|all] [дата]` | Аналітичний звіт прямо в консоль |
| `export [day\|week\|month\|all] [дата]` | Той самий звіт, але у Markdown-файл (`./reports/`) |
| `scope` / `scope add\|remove\|clear` | Керує фокусом звітів — які репо в них включати |
| `diagnostics` | Стан системи: токен, ціль, лічильники БД |
| `status` | Поточна фаза проєкту з `roadmap.yaml` |
| `decisions` | Список невирішених архітектурних питань |
| `decide <ID> <Варіант>` | Зафіксувати рішення з `decisions` |
| `set_target <username>` | Змінити GitHub-профіль для відстеження (потрібен рестарт) |
| `idea <текст>` | Швидко занотувати думку (⚠️ нікуди не зберігається, див. нижче) |
| `clear` | Очистити екран |
| `exit` | Вийти з консолі |

---

## report

```
report [day|week|month|all] [дата]
```

Друкує звіт прямо в консоль: кількість подій/комітів за період, розподіл
активності по репозиторіях, і список останніх дій (10 записів для `all`,
50 — для будь-якого конкретного періоду).

| Виклик | Період |
|---|---|
| `report` | За весь час |
| `report day` | Останні 24 години (рухоме вікно від "зараз") |
| `report day 2026-08-01` | Конкретний календарний день |
| `report week` | Останні 7 днів |
| `report week 2026-08-01` | Тиждень (Пн–Нд), що містить цю дату |
| `report month` | Останні 30 днів |
| `report month 2026-08` | Конкретний календарний місяць |

Якщо активний **scope** (див. нижче) — звіт автоматично фільтрується лише по
репозиторіях з фокусу, про що прямо написано в рядку `Фокус:` над звітом.

---

## export

```
export [day|week|month|all] [дата]
```

Синтаксис періоду ідентичний `report`. Різниця — результат не друкується в
консоль, а зберігається як файл `./reports/exarchon_report_<timestamp>.md`.
Кожен виклик створює **новий** файл (нічого не перезаписується), у ньому:

- High-Level Metrics (події, коміти, активні репо, сумарно `+X/-Y` рядків
  по останніх пушах у вибірці)
- Effort Distribution — розподіл по типу роботи (feat/fix/docs/...) на основі
  Conventional Commits у повідомленнях
- Code & Architecture Updates — список пушів, для кожного, де дані вже
  зібрані: `(files: N, +X/-Y)`
- Local Knowledge Base — активність по локальних `.md`-нотатках
- Заголовок звіту завжди явно показує застосований **Period** і **Report Scope**

## scope

```
scope
scope add <owner/repo>
scope remove <owner/repo>
scope clear
```

Визначає, які саме репозиторії потрапляють у `report`/`export`. Це окремо від
того, що́ демон взагалі відстежує (`tracked_repos` — увесь публічний
GitHub-профіль, автовиявлення) — scope лише звужує, що з цього йде у звіт.

- `scope` без аргументів — показує поточний фокус і повний список
  відстежуваних репо з позначками `[x]`/`[ ]`.
- `scope add` **звіряє назву з реально відстежуваними репо**. Одрук →
  підказує до 3 найближчих співпадінь. Репо, якого там немає взагалі
  (неіснуюче або приватне — автовиявлення бачить лише публічні репо) →
  окреме пояснення чому.
- `scope clear` — знову звітувати про все.

## diagnostics

```
diagnostics
```

Без аргументів. Знімок поточного стану: цільовий GitHub-профіль, чи
завантажений `GITHUB_TOKEN`, скільки подій/нотаток/відстежуваних репо в БД,
інтервал циклу демона. Перше, що варто перевірити, якщо звіти виглядають
порожніми чи застарілими.

---

## status

```
status
```

Без аргументів. Друкує `current_phase` з `config/roadmap.yaml` і статус
модулів (наразі завжди `ONLINE` — це не жива перевірка, а статичний напис).

---

## decisions

```
decisions
```

Без аргументів. Список усіх записів `decision_queue` з `roadmap.yaml` зі
статусом `pending`, разом з варіантами відповіді. Якщо черга порожня —
`[DECISIONS] Черга чиста.`

---

## decide

```
decide <ID> <Варіант>
```

Приклад: `decide dec_001 A`. Знаходить рішення з таким `ID` у `pending`
стані, позначає `resolved` з обраним варіантом, зберігає назад у
`roadmap.yaml`, і публікує подію `decision.resolved` на внутрішню шину
(`src/core/bus.py`) — це те, на що зможе підписатись майбутній Telegram-бот.

Варіант завжди переводиться у ВЕРХНІЙ РЕГІСТР (`a` → `A`). Неіснуючий `ID`
або вже вирішене рішення — команда просто нічого не робить і нічого не
друкує (без повідомлення про помилку).

---

## set_target

```
set_target <github_username>
```

Приклад: `set_target manikse`. Записує новий цільовий профіль у
`system_config` (БД). **Зміни застосовуються лише після перезапуску
`main.py`** — демон читає це значення один раз при старті.

---

## idea

```
idea <довільний текст>
```

⚠️ **Наразі нічого не робить, крім друку підтвердження.** Повідомлення
`[IDEA] Збережено в локальний кеш.` — не відповідає дійсності: жодного
запису в БД чи файл не відбувається, після закриття консолі текст втрачається
безповоротно. Команда — заглушка під майбутню реалізацію.

---

## clear

```
clear
```

Очищає екран термінала (`cls`/`clear` залежно від ОС). Суто косметична.

---

## exit

```
exit
```

Завершує консоль. **Демон при цьому теж зупиняється** — це фоновий потік
одного процесу з консоллю, окремо він не живе.

---

## Нюанси, які варто тримати в голові

- Кольоровий вивід (`colorama`) — суто косметика, не впливає на дані.
- Порожній Enter нічого не повторює (`emptyline` навмисно перевизначений).
- `report`/`export`/`scope` — єдині команди, які реагують на **scope** і
  **period**. Решта (`status`, `decisions`, `diagnostics`) читають дані без
  фільтрів.
